Forced Alignment With whisper.cpp: Word-Accurate Captions on a Phone

Time every spoken word for captions and graphics by aligning whisper.cpp word timestamps to your known script - running on a phone.

Captions that drift half a second behind the voice look cheap. Graphics that appear before the narrator mentions them look broken. Both problems have the same cause: guessing when words are spoken. This tutorial shows how we stopped guessing.

Transcription versus forced alignment

There are two ways to get word timings from narration:

  • Transcription - run speech recognition and use whatever words it hears. You get timings, but the words may be wrong (names, numbers, homophones).
  • Forced alignment - you already know the exact text, because you wrote the script. You only need when each known word was spoken.

We have the script, so we use a hybrid: run speech recognition to get timed words, then align them to the script text. The captions use the script’s spelling; the timings come from the audio.

Step 1: Get word-level timestamps from whisper.cpp

whisper.cpp is a fast C++ implementation of Whisper that runs on CPUs, including ARM phones. Two flags make it produce one word per segment with timestamps:

ffmpeg -i narration.wav -ar 16000 -ac 1 narration16k.wav
whisper-cli -m ggml-base.en.bin -f narration16k.wav -t 4 \
  -ml 1 -sow -ojf -of narration -l en
  • -ml 1 limits segments to one token’s length; with -sow (split on word) each segment is one word.
  • -ojf writes full JSON, including millisecond offsets per segment.

On our phone, the base.en model with four threads ran at roughly 1.1x real time: a 30-second narration took about 33 seconds. That is acceptable for a background pipeline.

Reading the output in Python:

data = json.load(open("narration.json"))
words = [{"text": s["text"].strip(), "start": s["offsets"]["from"] / 1000, "end": s["offsets"]["to"] / 1000}
         for s in data["transcription"] if s["text"].strip()]

Step 2: Normalise both sides

Alignment compares words, so both sides must be normalised the same way: lowercase, apostrophes removed, punctuation stripped.

def norm(word):
    word = word.lower().replace("’", "").replace("'", "")
    return re.sub(r"[^a-z0-9]+", "", word)

A subtle bug we hit: when normalising whole paragraphs, removing newlines without inserting a space glued the last word of one paragraph to the first word of the next (“custody” + “On” became “custodyon”). Always replace non-alphanumeric characters with a space, then split.

Step 3: Align with sequence matching

Python’s difflib.SequenceMatcher finds the longest matching runs between two sequences - exactly what we need.

a = [norm(w) for w in script_words]
b = [norm(w["text"]) for w in recognised]
matcher = difflib.SequenceMatcher(a=a, b=b, autojunk=False)
for block in matcher.get_matching_blocks():
    for k in range(block.size):
        i, j = block.a + k, block.b + k
        timeline[i].update(start=recognised[j]["start"], end=recognised[j]["end"], matched=True)

Then we rescue near-misses: in “replace” regions of equal length, pairs whose spelling similarity is at least 0.75 are accepted (Whisper writes “naira” where the script says “Naira’s“, for example).

Set autojunk=False. With long narrations, the default heuristic treats frequent words such as “the” as junk and produces poor alignments.

Step 4: Interpolate what Whisper missed

Some script words are never matched - a number written as digits, a name Whisper misheard. For each run of unmatched words, we spread them between the neighbouring matched words, weighted by character length:

left = timeline[i - 1]["end"] if i > 0 else 0.0
right = timeline[j]["start"] if j < n else duration
weights = [len(w["w"]) + 1 for w in timeline[i:j]]

Longer words get more time, which matches how people speak far better than equal slices.

Finally, we enforce monotonic times, so a word never starts before the previous one.

Step 5: Measure coverage

The share of script words that matched directly is our quality signal. On our narrations it is usually 94-97%. Our quality control fails any video below 70%, because at that point captions are mostly interpolated guesses.

If speech recognition is unavailable, the engine falls back to a silence-aware proportional estimate - and marks the video so automatic publishing is blocked. Estimated timing is fine for a preview, not for a published caption.

Using the timeline

With a reliable word timeline, everything else becomes simple lookups.

Captions. Group words into chunks that fit two lines, break at sentence ends and pauses over 280 ms, and never end a chunk on a function word such as “a” or “the”. Highlight the active word.

Graphics on cue. To show a “Development 02” board when that development begins, search the timeline for its anchor phrase and use the first word’s start time:

hit = find_phrase_time(timeline, "Labour unions threaten nationwide shutdown")
board_start = hit["start"]

Our quality check then confirms that the board’s start equals the anchor’s first-word time, and that the first word was genuinely matched rather than interpolated.

Running whisper.cpp on Android

We run whisper.cpp inside a lightweight Ubuntu environment on the phone (via proot-distro) and call it from Termux. The model file for base.en is about 140 MB. small.en is more accurate but roughly twice as slow, and for clean synthetic narration base.en has been more than good enough.

Summary

  • Use speech recognition for timing, your script for text.
  • Normalise carefully and align with SequenceMatcher(autojunk=False).
  • Interpolate gaps by character length.
  • Track coverage and refuse to publish on estimated timing.
