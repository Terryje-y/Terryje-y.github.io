Running a Python Video Pipeline in Termux: Setup, Limits and Lessons

Run Python, FFmpeg and whisper.cpp on an Android phone with Termux: setup, real limits, and habits that keep a phone-based pipeline stable.

By News AI Engine Editorial Team Published November 21, 2026 3 min read
In this article

  2. Checking your FFmpeg build
  3. Speech recognition with whisper.cpp in proot
  4. Know your limits
  5. Habits that keep it stable

Our News AI Engine has done much of its work on an Android phone. That was partly necessity and partly an experiment: how far can a creator get with hardware they already own? Further than we expected - with some firm limits. This guide covers the setup and the lessons.

What Termux gives you

Termux is a terminal app for Android with its own package manager. It provides real builds of Python, FFmpeg (with libass, libx264 and many filters), Git, Node.js and SQLite. For anything that needs a standard Linux userland, proot-distro can run a full Ubuntu environment inside Termux without root.

pkg update
pkg install python ffmpeg git nodejs sqlite
python -m venv ~/pipeline/.venv
~/pipeline/.venv/bin/pip install requests python-dotenv pillow
termux-setup-storage        # grants access to shared storage (~/storage/shared)

Checking your FFmpeg build

Before designing around a filter, confirm your build has it:

ffmpeg -hide_banner -filters | grep -E " (ass|subtitles|xfade|zoompan|drawtext|blackdetect) "

Then test the specific options you plan to use. On our build, one xfade transition (slideup) crashed with a segmentation fault while all the others worked. We now keep a whitelist of verified transitions; see our montage article.

Speech recognition with whisper.cpp in proot

We run whisper.cpp inside the Ubuntu environment and call it from Termux:

proot-distro login ubuntu -- /opt/whisper/build/bin/whisper-cli \
  -m /opt/whisper/ggml-base.en.bin -f /tmp/narration16k.wav -t 4 -ml 1 -sow -ojf -of /tmp/narration

Files are exchanged through the container’s /tmp, which is a normal folder from Termux’s point of view. With four threads, base.en runs at roughly real time on our phone.

Know your limits

Memory. Our phone had about 7 GB of RAM, typically with around 2 GB available. Large FFmpeg filter graphs - for example, crossfading dozens of inputs at once - were sometimes killed by Android’s low-memory killer. The symptom is an FFmpeg exit with a negative return code and no error message. Split big graphs into groups.

Local AI models. A quantised 1.5-billion-parameter language model runs, but it is not good enough for news scripts. Useful vision-language models need far more memory than a phone has. We use hosted APIs for language and vision, and run speech recognition locally.

Headless browsers. A headless Chromium inside proot works when it is driven the way Remotion drives it: over the DevTools protocol, with the GPU disabled. Using its simple --screenshot mode hung in our setup. Browser-based rendering is also slow on a phone; we measured about 11 seconds of render time per second of video with Remotion.

Storage. Video work fills phones quickly. Our engine checks free space before every render, deletes temporary files after each stage, and avoids keeping duplicate copies of finished videos.

Background execution. Android aggressively suspends background apps. Take a wake lock while long jobs run, and exclude Termux from battery optimisation:

termux-wake-lock      # release later with termux-wake-unlock

Habits that keep it stable

  1. Make output fail-safe. If the terminal session that started a server closes, writing to standard output can raise [Errno 5] I/O error. Wrap stdout in a writer that ignores those errors, or log to files.
  2. Persist every stage. A phone restarts more often than a server. Save each stage’s output and resume from it.
  3. One worker at a time. Run heavy renders sequentially; parallel renders fight for memory and finish later than sequential ones.
  4. Use file locks for single instances. Two copies of a scheduler or worker can double-process work. An fcntl lock file prevents it.
  5. Make shared-storage output visible. Files inside Termux’s private home are invisible to the Gallery and file manager. Save finished videos to shared storage, and run termux-media-scan so they appear.
  6. Keep secrets in a private .env inside Termux’s home with mode 600, never in shared storage.

Is a phone a good production machine?

For learning, prototyping and modest daily output: yes, surprisingly. A phone can write scripts through APIs, record narration, align captions, edit shorts in a few minutes and render long videos slowly. For high volume or 1080p long-form at scale, a small Linux server or desktop will be several times faster - and the same Python code will run there unchanged, which is the best argument for building this way.
