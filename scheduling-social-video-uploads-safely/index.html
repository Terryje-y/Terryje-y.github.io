Scheduling Social Video Uploads Safely: Idempotency, Missed Slots and Restarts

Build a publishing scheduler that never double-posts, never dumps overdue videos at once and survives restarts - fixed slots and SQLite.

By News AI Engine Editorial Team Published November 21, 2026 4 min read

A scheduler that posts videos at set times sounds like a cron job. In practice it has to answer harder questions. What happens if the device was off at 11:00? If the server restarts halfway through an upload? If the render finished after its slot? This tutorial describes the scheduler in our engine and the rules that make it safe.

Fixed slots instead of free-form times

We publish into five fixed daily slots in the channel’s local timezone: 07:00, 11:00, 14:00, 17:00 and 20:00. Users never pick dates or times; the scheduler assigns them.

def compute_slots(account, count, now):
    earliest = now + timedelta(minutes=10)          # never a slot that is about to pass
    taken = slots_already_assigned(account)
    out = []
    for slot in slot_iter(earliest):                 # walks day by day through the five slots
        if slot.isoformat() not in taken:
            out.append(slot)
            if len(out) == count:
                return out

Seven videos created at 06:00 get all five of today’s slots and the first two of tomorrow’s. The schedule is shown to the user before production starts.

Two details matter:

  • Timezones. Store everything in UTC; convert only for display. If your environment lacks timezone data, fall back to a fixed offset only for timezones without daylight saving.
  • A database constraint prevents two live videos holding the same slot for the same account, even if two requests race:
CREATE UNIQUE INDEX idx_slot ON videos(account_id, scheduled_at)
WHERE scheduled_at IS NOT NULL AND status NOT IN ('FAILED', 'CANCELLED');

The tick loop

A background thread runs every 30 seconds. Each tick:

  1. writes a heartbeat (so the dashboard can show “healthy” or “stale”);
  2. polls the status of uploads TikTok is still processing;
  3. looks at due videos and decides what to do with each.

Rule 1: Claim before you upload

The most important line in the scheduler is a conditional update:

UPDATE videos SET status='UPLOADING', publish_state='claimed'
WHERE id=? AND status='SCHEDULED' AND publish_id='';

Only if exactly one row changed does the tick proceed to call the API. Two ticks, two threads or two processes can never upload the same video, because only one of them can win the claim.

We also allow only one scheduler process per device, enforced with an OS file lock.

Rule 2: Overdue is not “post now”

If the phone was off for four hours, five videos might be due when it wakes. Posting them all at once looks like spam to viewers and to the platform. Our policy:

  • inside a grace window (20 minutes by default), publish normally;
  • beyond it, record a missed event and move the video to the next free slot (or hold it for the user, if they prefer);
  • at most one publish per account per tick, and at least 30 minutes between publishes per account.

The dashboard counts missed slots, so a recurring problem (battery optimisation killing the app, for example) is visible.

Rule 3: Restarts must never cause duplicates

Consider a restart at each point of an upload:

Restarted while… What we know Safe action
claimed, before the API returned a publish_id unknown whether TikTok created a post mark FAILED and ask the user to check the app before retrying
uploading chunks (have publish_id) the upload is incomplete; TikTok discards it mark FAILED with instructions; manual retry
processing (upload finished) TikTok has the video keep polling status

The rule: if we cannot be sure the platform has nothing, we never retry automatically. A missing post is a small problem; a duplicate post is a visible one.

Rule 4: Published means confirmed

The scheduler marks a video PUBLISHED only when the platform reports completion. Upload success alone moves it to UPLOADING/processing. If status stays unresolved for three hours, it is marked for manual checking rather than guessed.

Rule 5: Quality gates and modes

  • Videos that failed automated quality control are never published automatically.
  • Batches created in render-only mode never call the publishing API, even though their slots are recorded for manual posting.
  • A render that finishes after its slot is moved to the next free slot before it is ever considered for publishing.

Device realities

Our scheduler runs on an Android phone. That brings honest limits: nothing posts while the phone is off, the app is killed, or the server is stopped. We hold a wake lock while the server runs, recommend excluding the terminal app from battery optimisation, and make every gap visible through heartbeats and missed-slot records. A scheduler that admits its limits is more trustworthy than one that silently skips posts.

Testing it

All of these rules are covered by automated tests with a mocked platform API: slot assignment for 1, 3, 5 and 7 videos; claim-once idempotency; overdue rescheduling without bursts; one publish per tick; restart recovery; and “upload succeeded, still processing” not being reported as published.

Summary

  • Fixed slots, assigned by the system, stored in UTC.
  • A unique index plus a conditional “claim” update make uploads idempotent.
  • Overdue videos move; they never pile up.
  • When in doubt after a restart, stop and ask rather than retry.
  • Only confirmed publication counts as published.
