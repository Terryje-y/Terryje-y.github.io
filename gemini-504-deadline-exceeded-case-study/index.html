Why Our AI Scripts Kept Failing: A 504 DEADLINE_EXCEEDED Case Study

Our AI script stage failed more than it succeeded. The cause was timeouts, retries and fallback wiring - not the prompt. Diagnosis and fix.

News AI Engine Editorial Team November 21, 2026 · 4 min read

For a while, our script stage was the least reliable part of the whole engine. Looking at our AI call log, the primary model had 46 failures against 16 successes for long script drafting. Jobs ended in a red “failed” status, and the obvious conclusion was “the model is bad”. It wasn’t. This is how we found the real causes.

Step 1: Read the actual errors, not the summary

The dashboard only said “Script generation failed”. The structured log told a more useful story. Grouping failures by error type gave three buckets:

Error Share Meaning
504 DEADLINE_EXCEEDED most The request ran out of time on the server side
503 UNAVAILABLE (“high demand”) many The model was overloaded
429 RESOURCE_EXHAUSTED some Daily quota used up

There were also a handful of non-AI failures that had been blamed on the model: [Errno 5] I/O error and [Errno 103] Software caused connection abort. We come back to those below.

Step 2: Reproduce with the smallest possible request

We sent the same model a trivial prompt: Reply with exactly: OK. With a 60-second timeout it returned 504 DEADLINE_EXCEEDED after 65 seconds. With no timeout it succeeded - after 85 seconds, for a two-character answer.

A different model in the same family answered the same prompt in 1.6 seconds.

That reframed the problem completely. The prompt was irrelevant; the model was queueing requests under heavy demand.

Step 3: Understand what the timeout actually does

The SDK we use forwards the client timeout to the server as the request deadline. So a 180-second timeout does not just mean “give up after 180 seconds”; it tells the server “you have 180 seconds”. A long script that needed 120 seconds of generation, on top of 85 seconds of queueing, could never finish in time. The 504 was the server honestly reporting that.

Retrying the same model immediately - which is what a naive retry loop does - just joins the back of the same queue.

Step 4: Find the wiring mistakes

With the root behaviour understood, three design problems stood out in our original router:

  1. One provider’s permanent error killed the job. A configuration error from one provider (for example “reasoning is mandatory for this endpoint”) raised immediately, even though another provider was available and healthy.
  2. The fallback was random. The secondary route used an aggregator endpoint that picked a different free model on every call. Scripts came back in different styles and lengths, and validation failed unpredictably.
  3. Overload was treated like a network blip. The code retried in place instead of moving on.

Step 5: The fix - classify, then route

We rebuilt the router around one idea: what kind of failure is this, and what is the right next move?

def classify_error(exc):
    text = str(exc).lower()
    status = getattr(exc, "status_code", None)
    if "deadline" in text or status in (503, 504) or "high demand" in text:
        return "overloaded"      # move to the next model now
    if status == 429 and "quota" in text:
        return "quota"           # cool this model down, move on
    if status == 429:
        return "rate_limit"      # short backoff, one retry
    if status in (400, 401, 403, 404):
        return "config"          # skip this model, keep the job alive
    if is_network_error(exc):
        return "network"         # retry the same model with backoff
    return "server"

Each model has its own timeout, and the chain moves on quickly when a model is overloaded:

"model_chains": {
  "gemini": ["primary-model", "faster-model", "open-weight-model"],
  "openrouter": ["free-model-a", "free-model-b"]
},
"model_timeouts": {"primary-model": 240, "faster-model": 120}

A circuit breaker records consecutive failures per model. After three failures - or immediately for quota and configuration errors - the model is skipped for ten minutes, so the next job does not waste four minutes rediscovering the same outage.

Step 6: Fix the non-AI failures too

[Errno 5] I/O error came from print(). The dashboard server had been started from a terminal session that later closed; the next print() raised an I/O error and killed the job thread. The fix was a small wrapper around standard output that swallows write errors. It had nothing to do with AI at all.

[Errno 103] was a genuine network drop on a phone switching between connections. That should be retried on the same model, with backoff - so the classifier treats it as network.

Step 7: Validate, and give the model one chance to repair

Even with good routing, a model can return valid JSON that is still unusable - for example, a script 30 words too short. Rejecting it and moving to the next model throws away a mostly-good answer. Instead the router sends one repair request with the exact reason:

YOUR PREVIOUS ANSWER WAS REJECTED: Narration has only 129 words; it needs 155. Return a corrected, complete answer.

In practice that single repair attempt fixed most length problems in about ten seconds.

Results

After the change, a script request survives the realistic failure sequence we see on a busy day: primary model overloaded → second model returns a short script → repaired → or falls through to a free model. Failures that remain are reported with the full chain of reasons, instead of a single misleading message.

Lessons for your own pipeline

  • Reproduce with a trivial prompt. It separates “the model is slow” from “my prompt is too big”.
  • Know what your timeout means. In some SDKs it is a server-side deadline.
  • Classify errors before retrying. Overload, quota, configuration and network failures each need a different response.
  • Never let one provider’s configuration error end a job when another provider can do the work.
  • Log every attempt with provider, model, error type and duration. Without that log, we would still be blaming the prompt.
