Building a Multi-Provider AI Router With Fallbacks, Circuit Breakers and Validation

A practical Python design for calling several AI providers reliably: model chains, error classes, repair retries, health and cost logs.

By News AI Engine Editorial Team Published November 21, 2026 4 min read

If your content pipeline depends on one AI model, your pipeline is exactly as reliable as that model on its worst day. Ours depends on language models for scripts, vision models for footage analysis, and both for planning graphics. This guide describes the router we built so that a slow or failing provider becomes a short delay instead of a failed video.

It is written in plain Python with requests and the official SDKs. No framework is required.

Requirements

Before writing code we listed what the router must do:

  1. Route by task. Scripts, vision and descriptions need different models.
  2. Fall back to other models and providers on failure.
  3. Treat failures differently depending on their cause.
  4. Validate outputs and reject unusable ones.
  5. Remember provider health across jobs.
  6. Record usage and cost for every call.
  7. Never hang forever, and never retry forever.

Task routes and model chains

The configuration separates which providers a task may use from which models each provider tries:

{
  "task_routes": {
    "script":   ["gemini", "openrouter"],
    "vision":   ["gemini", "openrouter"],
    "planning": ["gemini", "openrouter"]
  },
  "model_chains": {
    "gemini":     ["large-model", "fast-model", "open-weight-model"],
    "openrouter": ["free-text-model", "free-vision-model"]
  },
  "vision_chains": {
    "gemini":     ["fast-model", "large-model"],
    "openrouter": ["free-vision-model"]
  },
  "model_timeouts": {"large-model": 240, "fast-model": 120},
  "retry": {"attempts_per_model": 2, "base_delay_seconds": 4, "max_delay_seconds": 45},
  "circuit_breaker": {"failures": 3, "cooldown_seconds": 600}
}

At runtime, the router flattens these into an ordered candidate list - for example gemini/large → gemini/fast → gemini/open-weight → openrouter/free-text - and filters out any model currently cooling down.

Avoid “auto” routes for production. An aggregator endpoint that picks a random model per request is convenient for experiments, but it makes output style and length unpredictable. Pin explicit models.

Error classification

The heart of the router is a function that turns any exception into one of a few categories, each with a fixed response:

Category Typical cause Response
network connection reset, DNS failure retry the same model with backoff
server HTTP 500 retry once
rate_limit HTTP 429 (per-minute) back off (respect Retry-After), retry once
overloaded HTTP 503/504, “deadline exceeded” move to the next model immediately
quota daily quota or zero credit cool the model down, move on
config 400/401/403/404, unsupported parameter skip the model, keep the job alive
invalid empty output, bad JSON, failed validation one repair attempt, then move on

The key insight is that only network, server and rate-limit errors justify retrying the same model. Retrying an overloaded model just re-queues you behind everyone else.

The core loop

def run(prompt, task, validator=None, json_mode=False):
    failures = []
    for provider, model in candidates(task):
        for attempt in (1, 2):
            started = time.monotonic()
            try:
                result = call(provider, model, prompt, json_mode=json_mode)
                data = extract_json(result["text"]) if json_mode else result["text"]
                if validator:
                    data = validator(data)          # raises on unusable output
                health_ok(provider, model)
                record_usage(task, provider, model, True, time.monotonic() - started, result.get("usage"))
                return data, result
            except Exception as exc:
                kind = classify_error(exc)
                failures.append((provider, model, kind, str(exc)[:300]))
                health_fail(provider, model, kind)
                record_usage(task, provider, model, False, time.monotonic() - started, error=kind)
                if kind == "invalid" and attempt == 1:
                    prompt += f"\n\nYOUR PREVIOUS ANSWER WAS REJECTED: {exc}\nReturn a corrected answer."
                    continue
                if kind in ("network", "server", "rate_limit") and attempt == 1:
                    time.sleep(backoff(attempt))
                    continue
                break                                   # next model
    raise AllProvidersFailed(failures)

The exception that finally escapes includes every failure in order. When a job fails, the dashboard can show “fast-model: overloaded; free-text-model: invalid (49 words)”, which is far more useful than “AI error”.

Validators: the router’s quality gate

A validator is just a function that receives the parsed output and either returns a cleaned version or raises. For our scripts it checks:

  • the narration length is within range for the target duration;
  • the first sentence is a hook, not “Welcome back to the channel”;
  • no headings, stage directions or markdown remain;
  • every “anchor phrase” actually appears word-for-word in the narration;
  • the narration addresses at least one meaningful word from the headline.

Because validators run inside the router, a model that returns well-formed but useless output is treated as a failure and the next model gets a chance.

Health and circuit breaking

Health is stored in a small JSON file so it survives restarts:

"gemini:large-model": {"consecutive_failures": 3, "cooldown_until": 1795250000, "last_error_kind": "overloaded"}

A model enters cooldown after three consecutive failures, or immediately after a quota or configuration error. Validation failures do not count toward the breaker: a model that writes a slightly short script is not unhealthy.

If every candidate is cooling down, the router tries them anyway rather than failing instantly. It is better to attempt a call than to refuse work based on old information.

Usage and cost tracking

Every attempt - success or failure - is written to a database table: timestamp, task, provider, model, duration, tokens and estimated cost. Some providers return cost directly; for others we keep a price table and leave cost empty when the price is unknown rather than guessing.

That table answers practical questions quickly: which model actually does our scripts, how often fallbacks happen, and what a day of production costs.

Vision requests through the same router

Images travel through the same loop. The provider functions accept a list of image bytes and attach them in each provider’s format (inline parts for one SDK, base64 data URLs for an OpenAI-compatible API). The output schema and validator stay the same, so a free vision model can take over when the primary is overloaded without the rest of the pipeline noticing.

Things that bit us

  • Reasoning text in content. Some models return their reasoning inside the answer. Strip <think> blocks and request that providers exclude reasoning from content.
  • System prompts on open-weight models. Some endpoints reject a separate system instruction. Fold it into the user prompt for those models.
  • Unsupported parameters. A “minimal thinking” setting accepted by one model returned HTTP 400 from another. Treat 400 as configuration, not as a reason to fail the job.
  • Console output. Make logging failure-proof. Our router once crashed because a terminal had closed.

Summary

A good router is mostly bookkeeping: explicit routes, honest error categories, a repair step, health memory and a usage log. None of it is glamorous. All of it is the difference between “the AI failed” and a finished video.
