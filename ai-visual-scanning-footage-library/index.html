AI Visual Scanning of a Footage Library With Vision Models

Using vision-language models to describe a footage library once, cache it, and match shots to narration - with batching that cut calls by six.

News AI Engine Editorial Team November 21, 2026 · 4 min read

Our footage folders are not organised the way an editor would want. Files arrive with random names - long hexadecimal strings - and nothing in the filename says whether a clip shows a press conference, a crowd or a parliament chamber. To pick shots that match the narration, the engine first needs to see the library. This article explains how we do that with vision-language models, cheaply and reliably.

The goal: one structured description per asset

For every video clip and still image, we want the same small record:

{
  "description": "A speaker addresses reporters at a podium in front of flags.",
  "people": ["man in traditional attire at podium"],
  "setting": "press_conference",
  "shot": "medium",
  "ocr_text": "BREAKING",
  "tags": ["speech", "podium", "media", "government"],
  "has_face": true,
  "face_x": 0.52,
  "quality": 4,
  "graphic_violence": false
}

Each field has a job:

  • setting and tags drive matching against what the narrator is saying.
  • face_x tells the cropper where the subject is horizontally, so vertical crops keep faces in frame.
  • quality pushes blurry or watermarked clips down the ranking.
  • graphic_violence excludes footage that should never appear in a general-audience video.

Rule: never identify people from faces alone

We instruct the model to name a person only if they are identifiable from on-screen text, captions or clear context, and otherwise to describe them. Face recognition of real people is a privacy and accuracy risk, and a wrong identification in a news video is a serious error. Descriptions such as “man in a dark suit at a lectern” are enough for matching.

Turning a video into one image

Vision APIs accept images, not videos. For each clip we extract three frames - at 20%, 50% and 80% of its duration - and join them side by side into a single “contact strip”:

ffmpeg -ss 2.1 -i clip.mp4 -frames:v 1 -vf scale=320:-2 f0.jpg
ffmpeg -ss 5.3 -i clip.mp4 -frames:v 1 -vf scale=320:-2 f1.jpg
ffmpeg -ss 8.5 -i clip.mp4 -frames:v 1 -vf scale=320:-2 f2.jpg
ffmpeg -i f0.jpg -i f1.jpg -i f2.jpg -filter_complex hstack=inputs=3 -q:v 6 strip.jpg

One small strip shows how the shot develops while staying a few kilobytes in size.

Batching: six assets per request

Sending one request per asset was slow and burned rate limits. Instead, each request carries six images, numbered in the prompt, and asks for an array of six records in the same order. For a library of 97 assets, that meant 17 requests instead of 97.

The validator checks that the array has the right length and repairs small problems, such as missing indices or out-of-range face_x values, before anything is saved.

Cache by content, not by run

Analysis results are stored in a database table keyed by file path, together with file size and modification time. On the next scan, unchanged files are skipped. Adding ten new clips to a folder costs two requests, not seventeen.

If every provider fails for a group, the entries are saved with status failed and retried on the next scan. Production does not stop: unscanned assets can still be used, they just rank neutrally. Our quality report shows how many of a video’s clips had real analysis.

Matching shots to narration

Each montage slot lasts three seconds. For each slot we find the sentence being spoken at its midpoint, then score every asset:

score  = 1.0
score += 1.2 * overlap(asset_words, sentence_words)        # description, tags, OCR
score += 2.0 * overlap(asset_words, people_in_story)       # names in on-screen text
score += 1.5 * overlap(setting_hints[asset.setting], sentence_words)
score += 0.4 * (asset.quality - 3)
score -= 2.5 * times_already_used(asset)                   # spread usage
score -= 6.0 if asset in last_three_shots else 0           # no immediate repeats
score += 0.6 if asset.is_video else 0                      # prefer motion over stills
score += 0.8 * seeded_random()                             # variety, reproducible per video

The setting hints are small vocabularies: a courtroom asset gets a boost when the sentence contains “court”, “judge”, “bail” or “ruling”; a parliament asset when it contains “senate”, “lawmakers” or “bill”. Simple, transparent and easy to tune.

Choosing a vision model

We route vision requests through the same multi-provider router as text. What mattered in practice:

  • Structured output reliability. Some free models produced good descriptions but malformed arrays; the validator and fallback handle that.
  • OCR quality. Reading on-screen captions is valuable for matching; larger models were noticeably better.
  • Cost and quotas. A large initial scan can exhaust a free daily quota. Scan once, cache forever, and schedule big scans outside production hours.
  • Open-weight options. Open-weight vision-language models (for example the Qwen-VL and Gemma families) are available through hosted APIs. “Open weights” does not mean free hosting - running them locally needs far more memory than a phone has.

Results

On our first full scan, all 97 assets were analysed successfully in 17 batched calls. The descriptions were accurate enough that clips of speeches, crowds and chambers now land on the sentences that talk about them, instead of appearing at random.

Takeaways

  • Convert clips to compact contact strips.
  • Batch several assets per request, and validate the batch.
  • Cache by path, size and modification time.
  • Score shots with simple, explainable rules.
  • Describe people; do not identify them from faces.
